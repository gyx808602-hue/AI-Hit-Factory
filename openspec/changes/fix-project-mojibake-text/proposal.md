## Why

项目中历史上多次出现中文文案被错误编码后写入源码或文档的情况，近期音色管理已确认存在同类问题。整体清理可以避免页面、测试、OpenSpec 任务和进展文档继续传播乱码，降低后续开发判断成本。

本 change 与项目级 UTF-8 输出约束一致，只把这次“全项目乱码清理”的范围、验收和执行步骤沉淀为一次性变更，不重复改写全局工程规范。

## What Changes

- 扫描 `src`、`doc`、`openspec` 中常见中文乱码特征，区分运行时代码、测试断言、活跃 OpenSpec 文档、归档历史文档和进展记录。
- 优先修复会影响页面展示、测试语义和开发判断的 `src` 源码与测试文件。
- 修复活跃 OpenSpec change 和关键文档中的乱码内容，确保后续任务说明可读。
- 对归档 OpenSpec 文档和历史专题进展文档采用谨慎策略：仅在能从上下文可靠还原时修复；无法可靠还原时记录残留风险，不强行猜测。
- 增加或执行乱码残留扫描命令作为验收步骤，避免后续同类乱码再次进入关键源码。
- 不修改 API 契约、路由行为、React Query hooks、页面业务流程或 UI 组件结构。

## Capabilities

### New Capabilities
- `project-text-integrity`: 约束项目源码、测试和关键文档中的用户可见中文与任务说明必须保持可读 UTF-8 文本，不得残留常见 mojibake 乱码。

### Modified Capabilities
- 无。

## Impact

- 主要影响：`src/**/*.ts(x)`、`doc/**/*.md`、`openspec/changes/**/*.md`。
- 验证影响：需要执行乱码关键词扫描、相关定向测试，必要时执行 `npm run typecheck`。
- 不影响后端接口、依赖版本、构建配置和运行时数据结构。
- 当前工作区已有未提交改动，实施时必须避开无关文件，尤其不能覆盖用户已有改动。
