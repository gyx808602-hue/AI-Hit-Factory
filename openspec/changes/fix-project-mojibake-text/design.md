## Context

当前项目是 Vite + React + TypeScript 前端工程，用户可见中文主要分布在页面、feature 组件、测试 mock、OpenSpec 任务和 doc 进展文档中。历史上多次出现 UTF-8 中文被错误编码后写回文件的情况，表现为 `闊`、`璇`、`鏂`、`鍒`、`鈧`、`�` 等 mojibake 字符。

本次调研发现：

- `src` 当前仅剩 `src/pages/auth/LoginPage.test.tsx` 一处明显测试 mock 文案乱码。
- `openspec/changes/add-points-usage-statistics-page/tasks.md` 与归档 dynamic menu tasks 存在大段历史乱码。
- `doc/2026-07-02-mojibake-audio-menu-progress.md` 中保留了历史乱码样例，用于说明已修过的问题。
- 工作区已有未提交改动，包括刚完成的音色管理修复与 `src/features/text-image-video/form.ts` 的既有改动，实施时不能覆盖无关内容。

知识点拨：乱码修复不能像普通文案替换那样“看到哪改哪”。它更像后端数据迁移：先判断数据源、受影响范围和可逆性，再分批迁移。源码里的按钮文案可以从上下文和测试还原；历史任务文档如果缺少原始中文，就不能强行猜，否则会把错误内容写成“看起来正常”的新错误。

## Goals / Non-Goals

**Goals:**

- 清理 `src` 源码和测试中的可见乱码，避免页面、mock 数据和测试语义继续传播错误文本。
- 清理活跃 OpenSpec change 和关键项目文档中可可靠还原的乱码。
- 为无法可靠还原的历史归档文档建立残留记录，避免盲改。
- 使用 `rg` 关键词扫描、定向测试和必要的类型检查验证修复结果。
- 更新 `doc/progress.md` 记录完成范围、判断、下一步和验证结果。

**Non-Goals:**

- 不修改业务接口、路由、权限、React Query hooks、页面结构或 UI 组件抽象。
- 不批量删除历史文档或归档 change。
- 不对不可可靠还原的历史文档做猜测式翻译。
- 不引入新的编码检查依赖；优先使用现有脚本和简单扫描命令完成闭环。

## Decisions

1. **先修 `src`，再处理文档**

   Why：`src` 直接影响页面展示、测试语义和构建结果，优先级最高。文档乱码影响开发体验，但不会直接影响用户运行时。

   Alternative considered：一次性全仓库替换。放弃原因是乱码文本缺少一一映射，批量替换容易误伤历史记录、中文正常词和归档上下文。

2. **用关键词扫描作为验收门槛，不用复杂 AST 工具**

   Why：本次问题是文本编码污染，不是语法结构问题。`rg` 可以快速覆盖 `src/doc/openspec` 并输出精确位置，成本低、可复现。

   Alternative considered：新增 ESLint/自定义脚本。放弃原因是当前先做一次性清理，新增依赖和规则会扩大变更面；后续若乱码反复出现，再考虑脚本化门禁。

3. **文档分为活跃文档、归档文档和历史样例**

   Why：活跃 OpenSpec 文档会指导后续开发，必须优先可读；归档文档主要保留历史，无法还原时应记录风险；历史样例中出现乱码可能是被刻意引用，用于说明曾经的问题。

   Alternative considered：把所有文档乱码都删除。放弃原因是用户明确禁止擅自删除磁盘内容，同时删除会丢失历史定位信息。

4. **验证不改变业务行为**

   Why：乱码治理是文本完整性修复，不应引入页面结构、接口契约或状态流改动。相关页面测试应继续通过。

   前端类比：这次像修复 i18n 字典中的坏文案，而不是改页面组件树。后端类比：像修复种子数据或迁移脚本里的错误描述，而不是改接口 schema。

## Risks / Trade-offs

- [Risk] 归档文档缺少原始中文，强行还原可能写错历史事实。→ Mitigation：只修可从上下文可靠还原的内容；不可还原时记录残留与原因。
- [Risk] 关键词扫描可能命中“历史乱码样例”这类刻意记录。→ Mitigation：人工分类命中项，必要时在进展文档说明保留原因。
- [Risk] 当前工作区已有未提交改动，批量写文件可能覆盖用户内容。→ Mitigation：实施前后检查 `git status` 和目标文件 diff，只触碰本 change 目标文件。
- [Risk] 终端编码显示与文件真实 UTF-8 内容可能不一致。→ Mitigation：必要时使用 Node 按 UTF-8 读取确认真实文件内容，避免被 PowerShell 显示误导。
