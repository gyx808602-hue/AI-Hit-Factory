## Context

AI-Hit-Factory 是电商 AI 内容生产 SaaS 平台，积分体系负责承接 AI 生成任务的计费、企业用量追踪、充值、扣费、退款和审计。当前仓库已经落地 Vite + React + TypeScript 前端工程，使用 Ant Design、TailwindCSS、React Router 和现有应用壳页面；已有任务记录页、素材库页、数字人相关页，但缺少积分统计与积分使用记录入口。

用户要求创建 OpenSpec 任务：新增一个“积分统计”页面，里面是积分使用记录列表，操作列增加“详情”按钮。当前接口没有字段，先预留页面和字段契约。页面只借鉴用户图片的布局形式，颜色、字体、卡片、按钮、表格和整体视觉风格必须采用当前项目现有实现。

## Goals / Non-Goals

**Goals:**

- 在 OpenSpec 中定义积分统计页面的产品边界、技术方案、规格和实施任务。
- 后续实现时新增积分统计页，采用“顶部积分概览卡片 + 使用统计卡片 + 使用记录表格”的工作台布局。
- 颜色和视觉风格完全沿用当前项目现有页面，不为积分页新建独立主题、品牌色、卡片风格或按钮风格。
- 为真实接口未就绪的场景预留 TypeScript 字段、API Client、React Query hooks 和 Mock 数据。
- 使用服务端分页/筛选/排序形态设计积分记录列表，避免未来数据量增长时重构页面。
- 操作列提供“详情”按钮，详情以 Drawer 或 Modal 展示单条积分记录的完整字段。
- 接入静态路由注册表，预留动态菜单 `routeKey -> component` 映射和权限码。

**Non-Goals:**

- 不实现真实充值、支付、退款、发票或套餐购买流程。
- 不实现后端积分账户、流水表、任务扣费或退款逻辑。
- 不承诺当前阶段接口已经返回所有字段；字段先以前端契约和 Mock 数据预留。
- 不新增复杂 RBAC，只预留菜单权限码和路由守卫接入点。
- 不抽象全局通用 `BaseTable` 或复杂积分组件库；优先保持积分 feature 内局部实现。

## Decisions

### Decision 1: 积分页面归属 `points` 领域模块

积分统计页属于独立业务域，后续会关联账户、企业空间、任务扣费、充值和退款，因此后续实现应优先放在 `src/features/points` 或现有项目约定的积分相邻目录中，页面入口放在 `src/pages/PointsUsageStatisticsPage.tsx` 或等价路由页。

Why：积分不是任务记录页的附属表格，而是企业资产和计费审计的一部分。把类型、API 和 hooks 放到 `points` 领域中，可以避免页面直接拼装脆弱字段，也方便后续接入充值、退款、套餐等能力。

### Decision 2: 先定义前端契约，接口未定时使用 Mock 数据源

后续实现应先定义积分账户摘要和积分使用记录类型，例如：

- `PointsAccountSummary`: 当前余额、累计获得、累计消耗、冻结/待退积分、即将到期积分。
- `PointsUsageRecord`: 记录 ID、流水号、业务类型、积分变动、变动方向、余额快照、关联任务 ID、关联任务名称、操作人、企业空间、状态、发生时间、备注。
- `PointsUsageRecordDetail`: 在列表字段基础上补充扣费规则、退款状态、失败原因、原始业务单据和审计信息。

Why：接口字段未定时，如果页面直接写临时字段，后续联调会到处改 JSX。先把字段收口到类型和 API Client，未来真实接口变化只需要在适配层转换，页面保持稳定。

### Decision 3: React Query 管服务端数据，全局状态只放 UI 上下文

积分余额、积分流水、详情数据都属于服务端状态，后续实现必须通过 API Client + React Query hooks 获取，例如 `usePointsSummary()`、`usePointsUsageRecords(filters)`、`usePointsUsageRecordDetail(recordId)`。筛选条件可以是页面局部状态或 URL query，不应把记录列表复制进全局 store。

Why：积分流水会被充值、扣费、退款、任务重试等后端行为改变，React Query 更适合处理缓存、刷新和失效。全局 store 更像前端运行时上下文，适合侧边栏折叠、主题、当前企业空间这类客户端状态。

### Decision 4: 表格按服务端分页形态设计

积分使用记录属于会持续增长的审计型表格。后续实现即使先用 Mock，也必须保留分页、筛选和排序参数：页码、页大小、业务类型、方向、状态、时间范围、关键词。Ant Design Table 用于列表展示，并预留 `scroll.x` 以保证窄桌面窗口可用。

Why：前端一次性拉全量再分页只适合小数据。积分流水类似后端日志或订单流水，真实数据量会增长，必须按服务端分页模型设计，避免后期重做查询模型。

### Decision 5: 页面布局借鉴图片结构，但视觉风格采用现有项目

参考图片中“个人/积分概览卡片 + 使用统计 + 安全偏好列表”的结构形式，积分统计页建议：

- 顶部左侧：积分账户摘要大卡片，展示账户归属、当前余额、有效期提示、最近更新时间。
- 顶部右侧：积分消耗/充值摘要卡片，展示本月消耗、累计充值、待退款或冻结积分。
- 中部：使用统计卡片，展示按业务类型拆分的消耗占比。
- 下方：积分使用记录表格，操作列提供“详情”按钮。

Why：积分页面既要让用户快速看到“还剩多少”，也要能审计“积分花到哪里”。上方概览解决决策，下方流水解决追溯，信息层级清楚。颜色与风格不跟随参考图重新设计，是为了保持当前产品的一致性，避免同一 SaaS 工作台出现两套视觉语言。

### Decision 6: 详情使用 Drawer 或 Modal，优先不跳新页

积分记录详情是列表的附属查看动作，后续实现优先用 Ant Design Drawer 或 Modal 承载。详情内容包括基础流水信息、积分变动、关联业务、操作人、状态和备注。若未来详情包含复杂申诉、退款或任务链路，再升级为独立详情页。

Why：当前需求只要求“详情按钮”，没有复杂编辑流程。Drawer/Modal 可以减少路由复杂度，也更符合工作台里快速查看流水的操作习惯。

### Decision 7: 路由和权限只预留，不绕过后端复核

后续实现新增 route key，例如 `points.usageStatistics`，路径可暂定为 `/points/usage-statistics` 或与现有菜单命名保持一致。菜单权限码建议预留为 `points:usage:view`，详情按钮权限码预留为 `points:usage:detail`。

知识点拨：前端菜单权限像“按钮级开关”，能决定用户看不看得到入口；后端权限复核像“接口门禁”，决定用户即使绕过前端直接请求接口也不能越权。积分属于资产数据，所以后端必须最终复核企业空间、角色和权限。

## Risks / Trade-offs

- [Risk] 后端字段尚未确定，前端字段可能与真实接口有差异。→ Mitigation：先定义领域类型和适配层，真实接口接入时在 API Client 做字段映射。
- [Risk] 积分记录未来数据量较大，纯前端分页会卡顿。→ Mitigation：从 OpenSpec 阶段就要求服务端分页/筛选/排序形态。
- [Risk] 过早抽象通用表格会增加维护成本。→ Mitigation：积分表格先放在 points feature 内，只有跨多个页面稳定复用后再提升到 shared。
- [Risk] 视觉参考图偏个人中心风格，积分页面如果照搬颜色和装饰会与现有项目割裂。→ Mitigation：只采用图片的布局结构，颜色、卡片、按钮、表格和状态反馈全部沿用现有项目。
- [Risk] 用户可能误以为充值能力也在本次范围内。→ Mitigation：本 change 只做统计与使用记录，充值按钮可以作为禁用/占位入口或不纳入本期实现。

## Migration Plan

1. 后续实施前重新读取 `openspec/config.yaml`、`openspec/project.md` 和本 change 文档。
2. 新增 points 类型、Mock 数据、API Client 和 React Query hooks。
3. 新增积分统计页面和详情 Drawer/Modal。
4. 接入路由注册表、菜单元数据和权限码预留。
5. 补充页面测试、路由测试和 API 契约测试。
6. 执行类型检查、相关 Vitest 用例和必要的页面手动验证。

Rollback 策略：本变更为新增页面能力，若实现阶段出现问题，可移除新增路由入口并保留不影响现有页面；已定义的类型和 Mock 可随页面一起回滚。
