### 当前判断

- 这次问题的根因更像是“`/` 的首页分发策略不够稳”，而不是“登录页不会跳转”。
- 现有实现能处理“首个菜单项本身就是可访问路由”的简单情况，但当首项是目录、目录依赖 `redirect` 指向子路由，或者首个可见项最终并不在当前 `availableRoutes` 中时，就可能出现：
  - 登录后仍停在 `/`
  - 跳到不存在页面
  - 没有命中你期望的第一个有效目录菜单

## 阶段二：方案构思

### 方案 A：只改登录页默认跳转地址

- 修改点：`src/pages/LoginPage.tsx`
- 思路：登录成功时，不再先跳 `/`，而是直接计算并跳到一个业务路由。
- 优点：
  - 改动表面较小
- 缺点：
  - 登录页拿不到完整的动态菜单上下文
  - 与全站直接访问 `/`、刷新 `/`、token 恢复后访问 `/` 等场景语义不统一
  - 兼容性差，后续容易再次分叉

### 方案 B：继续保留 `/` 作为统一首页入口，在应用壳层做“首个有效目录菜单”分发

- 修改点：`src/app/App.tsx` 及相关测试
- 思路：
  - 登录成功后仍先跳 `/`
  - 在应用壳层基于当前菜单树、`redirect`、可访问路由集合统一计算“第一个有效目标”
  - `/` 只负责分发，不依赖某个具体页面是否被注释
- 优点：
  - 兼容登录后、刷新、手动访问 `/`、动态菜单开关切换等所有入口
  - 不需要改动你已经注释的路由页面
  - 与当前架构最一致，兼容性最好
- 缺点：
  - 需要把“有效目标”的判定逻辑写严谨，并补上回归测试

### 当前推荐

- 推荐采用 **方案 B**
- 原理上它更像后端网关统一分发入口：
  - 登录页只负责拿到身份态
  - 应用壳层基于当前用户真实可访问资源决定首页落点
- 这样即使你继续注释某些页面，`/` 仍能自动落到当前菜单树里第一个真正可用的目录目标

### 本次实现规则

- `/` 作为统一首页入口时，首页目标按以下优先级解析：
  1. 当前菜单项的内部 `redirect`
  2. 当前菜单项下第一个有效子菜单
  3. 当前菜单项自身 path
- 同时增加了“有效目标”校验：
  - 必须是内部路径
  - 不能是 `/`
  - 必须能在当前可访问路由集合中匹配成功
- 这样可以兼容以下场景：
  - 首项是目录菜单，但真正要落到子页面
  - 首项目录配置了 `redirect`
  - 首项 path 因为页面被注释或未注册而失效
  - 需要自动跳过无效首项，继续找下一个可访问菜单

### 为什么这个方案更稳

- 登录页本身不负责菜单理解，只负责登录成功后回到统一入口 `/`
- `App.tsx` 持有当前用户最终可访问路由、动态菜单树和隐藏路由集合
- 因此把首页分发放在这里，和后端网关按资源能力分发首页的原理一致：
  - 入口单一
  - 权限上下文完整
  - 不依赖某个被注释页面是否还存在

     - 这时 `canAccessProtectedRoutes = false`
     - 根路径 `/` 又没有静态注册页面

### 本次补强

  - 当访问 `/`
  - 且当前没有有效登录态
  - 直接跳转到 `/login?redirect=%2F`
  - 不再让用户看到 404
