# 2026-07-01 Axios 封装 B0001 不重登处理计划

## 背景

- 当前 `src/utils/request.ts` 将业务码 `B0001` 视为登录失效。
- 这会触发 `onAuthExpired -> redirectToLogin`，最终清空本地登录态并跳转登录页。
- 现需求变更为：当接口返回 `B0001` 时，不需要提示“重新登录”，只需要按普通业务错误提示即可。

## 方案构思

### 方案一：把 `B0001` 从“认证失效码”中移除

- 做法：
  - 保留 `A0230`、`A0231` 的认证失效处理。
  - `B0001` 不再进入 `onAuthExpired` 分支。
  - 让它走通用业务错误处理：弹错并抛出 `RequestBusinessError`。
- 优点：
  - 改动最小，风险最低。
  - 不影响现有真正的 token 失效链路。
  - 与“报错但不重登”的需求完全一致。
- 缺点：
  - 如果后端未来重新定义 `B0001` 为认证码，需要再次调整。

### 方案二：给 `B0001` 增加单独白名单分支

- 做法：
  - 保留 `B0001` 常量，但在响应拦截器中单独分支处理。
  - 明确写成“提示错误但不触发登录失效回调”。
- 优点：
  - 语义显式，便于以后继续扩展特殊业务码。
- 缺点：
  - 比当前需求多一层分支，复杂度略高。
  - 本质仍然是走普通业务错误流程，单独分支收益有限。

## 推荐方案

- 采用方案一。
- 原理上这相当于前端请求拦截器里的“错误路由表”收口：
  - 真正认证失效码继续走“全局登出中间件”；
  - `B0001` 回归普通业务错误处理。
- 知识点拨：
  - 后端里这类全局错误处理，类似前端的路由守卫或 axios 拦截器。
  - 一旦你把某个业务码放进“认证失效”分支，它就不再只是提示问题，而是会触发全局副作用，比如清 token、跳登录页。
  - 所以这次不是“改弹窗文案”，而是“把错误码从全局副作用链路里摘出去”。
